Every webhook receiver eventually gets the same event twice. The sender retried
because your acknowledgement was slow, or a deploy replayed a queue, or someone
clicked the button again. If the handler on the other end creates an invoice,
sending it twice is not a logging curiosity — it is a second invoice.

The standard fix is an idempotency key: derive a stable identifier from the
event, record it before you do any work, and refuse to do the work again if the
identifier is already there.

## The shape of it

The key has to come from the event, not from the moment you received it. A
timestamp or a generated UUID is different on the retry, which is exactly when
you need it to be the same.

```sql
create table processed_events (
  key         text primary key,
  event_type  text not null,
  received_at timestamptz not null default now(),
  result      jsonb
);
```

And the claim, in one statement:

```sql
insert into processed_events (key, event_type)
values ($1, $2)
on conflict (key) do nothing
returning key;
```

If that returns a row, this process owns the event and should do the work. If
it returns nothing, someone already claimed it — acknowledge and stop. The
primary key does the mutual exclusion for you, which means no advisory locks,
no `select` then `insert` race, and no dependency on the queue being
single-consumer.

The important part is the ordering: **claim before you work**. Claiming after
the work succeeds leaves a window where a retry arriving mid-flight does the
work a second time, which is the exact failure you were trying to prevent.

## What it doesn't fix

An idempotency key is a deduplication mechanism. It is not a correctness
mechanism, and treating it as one is where the confidence gets misplaced. Three
things survive it.

### Ordering

Two events about the same invoice can arrive out of order. Each has a distinct
key, so each is processed exactly once — and the final state is still wrong,
because the older update landed last. The key stops the second write of the
*same* event; it does not sequence *different* ones.

The fix is a version or sequence number on the entity, and a write that
declines to go backwards:

```sql
update invoices
   set status = $2, version = $3
 where id = $1
   and version < $3;
```

If the source system does not give you a monotonic version, its event timestamp
is usually the next best thing — with the caveat that clocks on the other side
of an API are not your clocks.

### Partial writes

If the handler makes four calls and the third fails, the key is already
claimed and the record is half-built. The retry arrives, finds the key, and
correctly refuses to run — leaving the half-built record there permanently.

Two ways out. Claim per hop rather than per event, so each call has its own key
and the retry resumes at the failed step. Or make the whole handler a single
transaction that either commits or leaves nothing behind — which works when
every write is in your own database, and does not when one of the hops is
someone else's API.

The one thing that does not work is claiming per event, doing four
non-transactional things, and hoping.

### Upstream duplicates

Sometimes the source system emits what is genuinely the same business event
twice, with two different event IDs. No key derived from those IDs can help,
because by every mechanical measure they are different events.

This one is not a technical problem. It needs a business rule — one invoice per
order per day, or a natural key built from the fields that actually identify
the thing rather than from the envelope around it. Write the rule down with the
client before you implement it, because you will be encoding their definition
of "the same event", and it is rarely the obvious one.

## Where the key should live

In the same database as the work, in the same transaction as the work, if you
possibly can. An idempotency table in Redis while the write goes to Postgres
gives you two systems that can disagree, and they will — usually during the
incident where you most need them not to.

## The rule

An idempotency key buys you exactly one guarantee: this specific message will
not be processed twice. That is worth having, and it is cheap. It is not
ordering, it is not atomicity, and it is not a substitute for agreeing what
counts as a duplicate in the first place.

Build all three. The key is the twenty minutes; the other two are the design.
