One index, every width.

The hero already floats a social pill at the top and a dot rail at the right. A second horizontal menu would be a third floating thing. So there is no menu bar: the top band gets a monogram on the left and an Index trigger on the right, the pill keeps the centre, and the navigation itself is a full-screen typographic index — the same one on a 4K monitor and on a phone.

Past the hero the band condenses to a hairline with the current section spelled out in mono and a 1px gradient scroll line. That line is the only place the gradient runs the full width of the page.

02 — About

Zubair builds the parts nobody wants to run by hand.

Zubair Bin Shaukat is a software engineer in Lahore, Pakistan. He has spent six years building the machinery agencies and founders run their businesses on: automation pipelines in n8n, custom dashboards and marketplace apps inside GoHighLevel, web applications in Next.js, and cross-platform mobile apps in React Native.

Most of the work starts the same way. A team has a process that works, as long as one specific person does it on a specific day. Zubair sits with that person, writes the process down until it stops having exceptions, and then builds the version that does not need them. The deliverable is not a tool — it is a system with a documented failure mode, a retry policy, and a named owner.

He works direct with founders and white-label for agencies, usually as the only engineer on the project. Twenty-eight of the thirty-four systems he has shipped are still in production. The other six were replaced by platform features, which he considers a good outcome.

Problem

The agency ran 42 client sub-accounts in GoHighLevel. Reporting meant one person opening each sub-account on Monday, copying six numbers into a shared sheet, and rebuilding a slide per client. Six hours a week, and the sheet was wrong often enough that account managers had stopped trusting it.

Three previous attempts had failed for the same reason: they exported data out of GoHighLevel into a BI tool, so account managers had to leave the place they actually worked. Adoption never got past the two people who built it.

There was also no shared definition of a qualified lead. Four sub-accounts tagged it on the form, two on the call outcome, the rest not at all.

Approach

We agreed the definitions before writing any code — two sessions, one page of output. Then the dashboard was built as a custom menu link inside GoHighLevel, so it opens where the work already happens.

Monday reporting went from six hours to an eleven-minute review of exceptions. Thirty-eight of the 42 account managers open the dashboard at least weekly — measured, not assumed. Two client renewals were credited to the new report in the following quarter.

What did not go to plan: the first version polled the API per sub-account on page load and hit rate limits by the ninth account. It was rebuilt as a nightly sync into Postgres with a Redis cache for the current day, which is what shipped.

Handover was a 40-minute recorded walkthrough, a runbook covering the four failure modes, and the sync log above. The agency has since added two metrics themselves.

{{ post.title }}

A retry-safe pipeline is mostly a naming problem. Here is the key I use, why it lives in Postgres instead of n8n, and the three failure modes it does not solve.

The pipeline ran at 03:00 and filed invoices into Xero. It worked for five weeks. Then a depot's connection dropped mid-run, n8n retried the workflow from the top, and 61 invoices were filed twice. I found out at 08:40, from the client.

The bug was not the retry. The retry was correct. The bug was that my workflow had no way of saying this exact invoice has already been filed.

One key per business event

An idempotency key is a string that identifies the thing that happened, not the run that processed it. If you can generate it twice from the same input and get the same string, you can check it before you write.

// n8n Function node — deterministic, no clock, no run id
const src = $json.source;            // 'xero.invoice.created'
const id  = $json.entityId;          // stable upstream id
const day = $json.periodEnd.slice(0, 10);

return [{
  json: {
    ...$json,
    idemKey: `${src}:${id}:${day}`,
    attempt: $runIndex + 1,
  },
}];

No Date.now(), no $execution.id. Both change on retry, which is the whole problem.

Where the key lives

Not in n8n. Static data on a workflow is convenient and it is not a database — it has no unique constraint, and two concurrent executions will both read an empty value and both write. The key goes in a Postgres table whose only job is to say yes or no.

create table processed_event (
  idem_key    text primary key,
  workflow    text not null,
  created_at  timestamptz not null default now()
);

-- claim it or bail; the constraint does the arbitration
insert into processed_event (idem_key, workflow)
values ($1, $2)
on conflict (idem_key) do nothing
returning idem_key;

If the empty result means “someone else already has this”, you have moved the race from your workflow into the database, where it has been solved for forty years.

What it does not fix

The key stops duplicates. It does not make the pipeline correct. Three things still bit me afterwards:

The rule I use now

Before any node that writes to a system I do not own, there is a claim step. Before any pipeline goes live, I run it twice on the same input on purpose and check that the second run changes nothing. It takes ten minutes and it has caught something in four of the last six projects.

The 61 duplicates took two hours to reverse and one uncomfortable call. The claim table took twenty minutes to build.

10 — Design note

The Ledger — rules of the system.

Direction chosen: the site below the hero is an indexed ledger — numbered sections, hairline rules instead of cards, the display serif doing the headline work at every level, and mono carrying all metadata. The hero is the only spectacle; everything after it reads like a well-set spec sheet. Rejected: a dashboard-mimicking “console” site (too costume-y, and it competes with the actual dashboards in the work) and a cinematic full-bleed scroll (beautiful, slow, and hostile to skimming founders).
